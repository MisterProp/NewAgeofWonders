# Age of Wonders 1 - decompilation & C++ port workspace

This folder is a self-contained **workflow harness** for reverse-engineering
Age of Wonders 1 (1999) and growing a C++ re-implementation of it. It sits next
to the game so it can read the original binaries and data files in place.

```
port/
  README.md              <- you are here
  manifest.json          <- inventory of binaries + formats
  build.ps1              <- CMake-free build of the C++ skeleton
  run_pipeline.ps1       <- run every static-analysis / extraction stage
  docs/
    00_FINDINGS.md       <- what the binaries actually are (facts we verified)
    01_FORMATS.md        <- on-disk formats (ILB, PFS, MLD, HSS, ...)
    02_TOOLING.md        <- external tools to install (Ghidra, JDK, ...)
    03_ROADMAP.md        <- the staged decompile -> port plan
    04_DRIVING_CLINE.md  <- how to prompt/automate this agent per stage
    05_AUDIO.md          <- the audio path recovered with Ghidra + its C++ port
    06_TITLE_SCREEN.md   <- the main menu/title screen, recovered and reproduced
    07..17_*.md          <- the UI screens, units, movement and animation docs
    18_WATER_ANIM.md     <- the sea: the wave-phase tiles, foam, the ripple counter
    19_STRUCTURE_FLAGS.md <- the owner flag a "takeable" structure flies
    20_PARTY_WINDOW.md <- the Party floater (TControlWin) and its leave-behind
    21_ARMY_COUNTER.md <- the size shield + leader crown drawn over an army
  tools/                 <- Python (stdlib only) + Ghidra scripts
  re/                    <- reverse-engineering output (gitignored, regenerated)
  assets/                <- extracted game assets (gitignored)
  src/                   <- the C++ port (engine skeleton, builds today)
```

## TL;DR - the reality of "auto-decompiling the whole game"

Age of Wonders 1 is **not** a C/C++ game. It is a **Delphi / Borland Object
Pascal** application (32-bit PE, GUI subsystem), with the game logic split
across ~17 Delphi runtime packages (`*.dpl`) plus the main `AoW.exe`. That has
three big consequences for a "port":

1. A generic C decompiler (Ghidra/IDA/RetDec) will give you **C that compiles
   nowhere near a game** - no class model, mangled Borland names, Delphi
   `register` calling convention everywhere. It is excellent for *understanding
   individual routines*, useless as a "build this" source tree.
2. Delphi keeps **its own RTTI and VMTs**, published method names and
   **DFM form resources**. Those are recoverable and give you the UI layout and
   the class/method names for free - a far better starting point than raw C.
3. The **data is the game**. `.PFS` tables (unit stats, spells, items, heroes,
   abilities, terrain rules) and `.ILB` sprite banks *are* AoW. A faithful port
   is mostly: implement the engine (render/input/turn loop) + interpret the same
   data files.

So the workflow here is deliberately **hybrid**: recover structure & data
automatically, and re-write the engine in C++ guided by that structure. Plan
for this to be a long, incremental project, not a one-shot decompile.

## Quick start

Audio needs **libopenmpt** to decode the `.IT` soundtrack (MSYS2:
`pacman -S mingw-w64-ucrt-x86_64-libopenmpt`). `build.ps1` links `-lopenmpt` and
copies its runtime DLLs next to the executables; everything else builds with just
g++/clang++/cl.

```powershell
cd "c:\GOG Games\Age of Wonders\port"

# 1) Static extraction (no external tools, runs in seconds/minutes)
./run_pipeline.ps1

# 2) Build the port: bin/AoW.exe (the game, carrying the game's own icon),
#    bin/aow_view.exe (map viewer) and bin/aow_tools.exe (data-dump CLI)
./build.ps1

#    ...or build and install AoW.exe + aow_view.exe next to the game:
./build.ps1 -Viewer

# 3) (once Ghidra is installed - see docs/02_TOOLING.md) decompile everything
$env:GHIDRA_HOME = "C:\ghidra_11.1_PUBLIC"
./tools/ghidra/run_ghidra.ps1
```
